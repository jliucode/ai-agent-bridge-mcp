这两份文档的毛病主要集中在**对 Claude Code 能力的过度假设**，尤其是"自动心跳"部分。逐条分析：

---

## 一、核心毛病：自动心跳不可行

**文档声称：**
> "每 30~60 秒自动调用 agent_heartbeat"
> "在长任务执行期间也要保持心跳"
> "心跳无需用户催促，完全后台自动进行"

**实际情况：**
Claude Code **没有后台定时执行能力**。它是**纯对话触发**的 LLM 助手：
- 用户不发消息 → Claude Code 不运行
- 对话结束后进程即停 → 不存在 `setInterval` 或守护线程
- 所谓的"自动"只能是**用户每次发消息时顺带补一个心跳**，而非真正的后台定时心跳

**后果：**
如果用户 5 分钟没说话，agent 就会被 Bridge 标记为 OFFLINE，其他 agent 无法委派任务。文档给用户造成了"挂在那里就能保活"的错觉。

---

## 二、SSE 长连接 ≠ 心跳

**文档毛病：** 暗示 SSE 连接本身能维持 agent 在线状态。

**实际：**
- SSE 是**服务端→客户端**的单向推送通道
- `agent.heartbeat` 是**客户端→服务端**的独立 RPC 调用
- SSE 连接活着 ≠ 心跳已发送
- 如果 SSE 连接因网络抖动断开重连，session_id 可能变化，之前的注册状态直接失效

---

## 三、"首次对话自动注册"不成立

**文档声称：**
> "当用户说'注册到桥'或**首次对话时自动执行**注册流程"

**实际：**
Claude Code 的 Skill 触发依赖用户输入关键词（如 `/agent-bridge` 或"注册到桥"）。**不存在"首次对话自动执行"的机制**。如果用户第一次只是问"你好"，不会触发任何注册。

---

## 四、状态自动切换（IDLE/BUSY）是伪需求

**文档声称：**
> "空闲时 → IDLE；接到任务 → BUSY；完成后 → IDLE"

**实际：**
Claude Code 无法感知自己是否"空闲"。只要用户在对话中，它就是 BUSY；对话结束它就不存在了。状态切换只能由**用户口头指令**触发（如"更新状态为 IDLE"），而非自动判断。

---

## 五、task.assigned 事件接收有坑

**文档声称：**
> "当收到 SSE 事件 task.assigned 时（系统自动推送）"

**实际隐患：**
- Claude Code 必须**保持 SSE 连接**才能收到推送
- 但 Claude Code 是按需启动的，不会长时间挂起监听 SSE
- 如果任务委派时 Claude Code 不在线（SSE 未连接），事件直接丢失，不会有任何通知
- 文档没有提到**离线消息补偿**或**轮询 task_list** 的兜底机制

---

## 六、其他细节毛病

| 文档描述 | 实际问题 |
|---------|---------|
| "Claude Code 启动 → 自动连接 MCP" | 需要手动配置 `.mcp.json` 且服务可达，不是"自动" |
| "超过 60 秒无心跳标记 OFFLINE" | 对交互式工具来说过于严苛，正常对话间隔都可能超时 |
| "result 要写清楚做了什么修改" | Claude Code 没有文件系统持久化能力，跨会话无法追踪历史修改 |
| 多 Agent 协作示例 | 两个 Claude Code 实例需要两套独立 SSE 连接，文档未强调 session 隔离 |

---

## 七、如果要实现"自动心跳"，唯一可行方案

**必须引入外部守护进程**，Claude Code 本身做不到：

```bash
# 独立的心跳守护进程（Python/Node）
while true; do
  curl -X POST "http://bridge:8000/messages?session_id=xxx" \
    -d '{"method":"agent.heartbeat"}'
  sleep 30
done
```

或者把 Bridge 的**心跳超时阈值放宽到 1 小时以上**，接受"用户每次发消息时手动补心跳"的现实。

---

## 总结

| 功能 | 文档声称 | 实际可行性 |
|------|---------|-----------|
| 自动心跳 | ✅ 后台自动 | ❌ **不可行**，无后台执行能力 |
| SSE 事件接收 | ✅ 实时推送 | ⚠️ 需保持长连接，离线即丢 |
| 自动注册 | ✅ 首次对话自动 | ❌ 需用户触发 |
| 自动状态切换 | ✅ 自动 IDLE/BUSY | ❌ 需用户手动 |
| 多 Agent 协作 | ✅ 实时委派 | ⚠️ 受限于心跳和在线状态 |

**结论：** 文档描绘的是一个"理想化的常驻 Agent 系统"，但 Claude Code 本质是**按需启动的对话工具**。要实现文档中的全部能力，需要额外包装一个常驻进程（如 Electron 托盘程序或后台 Docker 容器）来代理 SSE 连接和定时心跳，而非 Claude Code 裸跑。
